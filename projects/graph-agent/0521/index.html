Core Insight

Feature interaction matters most.

For graph tasks, the gain comes from finding the right features, not from a bigger model.

Often credited

  • Model architecture changes
  • Neural network scaling
  • Switching to a more complex graph backbone

Actually decisive

  • Discovering useful feature interactions
  • Relational signal across hops
  • Time-windowed aggregates of neighbors

Evidence 1 — Wide & Deep [1]

Explicit feature crosses still earn their keep alongside a deep network.

  • Wide: memorize sparse cross-products
  • Deep: generalize dense embeddings
  • Combined beats deep-only

Evidence 2 — GADBench [2]

XGBoost + aggregated neighborhood features outperforms graph/neural models with raw features.

The decisive factor is not the backbone — it's whether the model receives strong relational features.

Design commitment. Make the feature set the search target. Hold the evaluator constant.

Framework · Principles 1 & 2

Search over feature sets, in a small typed grid.

Fix a strong default evaluator. Vary features over hop × time.

Search target:
feature set

Fixed:
XGBoost / LightGBM evaluator

Faster evaluation · stable comparison · clean attribution to feature interactions

0-hop Zero-hop

Local transforms on the target entity.

column transform · normalization · bucketization

1-hop One-hop

Aggregate from directly connected entities.

transactions → account features

2-hop Two-hop

Aggregate through a two-step relational path.

receiver history → back to sender

Static connection

Use existing graph/table relations. No temporal window.

Temporal window

Use only historical relations within a time window.

Why this grid. Small, complete taxonomy → controller can plan; worker has a typed slot to fill.

Two concrete operators

From spec to feature, in two flavors.

The simplest static aggregate, and a temporal two-hop with real bite.

1-hop · staticAggregate transactions → account
target:   account
path:     account <- transaction
values:   transaction_amount,
          transaction_type,
          merchant_category
agg:      sum / mean / count / max

Resulting features

account_total_transaction_amount
account_avg_transaction_amount
account_transaction_count
2-hop · temporalReceiver's 7-day history → sender
target:   sender_account
path:     sender_account
          -> transaction
          -> receiver_account
window:   receiver inbound [t-7d, t)
values:   amount, count,
          transaction_status
agg:      sum / count / failure_rate

Resulting features

receiver_7d_incoming_amount_sum
receiver_7d_incoming_txn_count
receiver_7d_failed_payment_rate
Why the temporal one bites. Captures whether the sender is interacting with an unusually active or suspicious counterparty right now.

Framework · Principle 3

Typed specs & controller-worker parallelism.

Two engineering lessons that cut the failure rate and unlock throughput.

Lesson 1Each Feature OP is a typed, validated spec
target_entity: sender_account
path:
  - sender_account -> transaction
  - transaction -> receiver_account
value_columns: [amount, transaction_status]
temporal_window: 7d
aggregation: [sum, count, failure_rate]

Validation catches

invalid relation path · missing raw column · incompatible type · invalid window · feature leakage risk

Summary

Graph Foundation Agent — in one slide.

Scale the discovery of features, not the size of the model.

What we demonstrate

  • 1Graph performance is bottlenecked by feature interaction discovery, not architecture.
  • 2Search over 0-, 1-, 2-hop feature operators × static/temporal.
  • 3Each feature = typed, validated Feature OP spec.
  • 4Controller orchestrates parallel workers proposing & evaluating candidates.
  • 5Boosting-tree evaluators give fast, fair feedback.
Instead of scaling a single graph neural architecture, we scale the discovery of useful relational feature interactions.

Status

#1 average on GraphTestbed — best on 3 of 4 tasks among compared agents.
